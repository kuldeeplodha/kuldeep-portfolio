**Media is the usual trap:** Storing many images/videos in the git repo bloats the repo and hits GitHub's recommended 1 GB soft limit quickly. Git LFS has a strict 1 GB bandwidth cap per month — blows past it with any real traffic. **Cloudinary free tier (10 GB, 20 GB CDN) is the correct zero-cost answer for media.** No card required. Suitable for a personal portfolio indefinitely.

## 1. Option A — Git-Based CMS (Stay on GitHub Pages)

**How it works:** A CMS (Decap CMS or TinaCMS) authenticates to GitHub via OAuth, writes Markdown/JSON files directly to the repo, and triggers a GitHub Actions rebuild. Content lives in git; GitHub Pages serves the output.

### A1 — Decap CMS (formerly Netlify CMS) — **ZERO COST, RECOMMENDED**

| Factor | Detail |
|--------|--------|
| **Cost** | $0. MIT open source. No paid plan ever required. |
| **Card required?** | No. |
| **Auth model** | GitHub OAuth. Decap needs an OAuth proxy to complete the GitHub OAuth flow in the browser (CORS restriction). **Free path:** deploy the community `netlify-cms-oauth-provider` (Node.js, ~50 lines) to a **Render free web service** (spins down after 15 min idle, auto-resumes on next login — acceptable for infrequent admin sessions). Alternative: Netlify Identity (Netlify free tier, no Pages move needed — just deploy the proxy there). |
| **Free tier limits** | Render free: 750 compute hours/mo (sufficient for OAuth proxy that only wakes on admin login). GitHub Actions: 2,000 minutes/mo free (a 60s blog-post build uses ~1 min; ~2,000 posts/mo ceiling — never a real limit). GitHub Pages: unlimited. |
| **Media storage** | **Do NOT store images in the git repo** (repo bloat, 1 GB soft limit). Use **Cloudinary integration**: Decap natively supports a `cloudinary` media library config. Free Cloudinary: 10 GB storage, 20 GB CDN bandwidth, 25 credits/mo — no card required. Sufficient for hundreds of blog images indefinitely. |
| **At the ceiling?** | Cloudinary 25 credits/mo is the only real ceiling. At ~10+ posts/mo with many large images, credits could run low. Mitigation: compress images before upload; use `f_auto,q_auto` transforms. |
| **Complexity** | Low-medium. Single `static/admin/config.yml` defines collections. No schema code. UI is form-based (not visual editing). |
| **GitHub Pages** | Stays as-is. Rebuild via GitHub Actions on every content push (~60s). |
| **Blog migration** | Existing `src/content/blog/*.md` files are natively compatible — zero migration work. |
| **Case studies** | Define a new collection pointing at `src/content/case-studies/*.md`. Frontmatter fields map to the case study shape. |
| **Rebuild time** | ~30–90 seconds (GitHub Actions). Not instant; suits infrequent publishing. |
| **Maturity** | ~18k GitHub stars, production since 2016. Form-based editor UI. Development pace post-rebrand is slower than TinaCMS but zero vendor dependency. |

### A2 — TinaCMS

| Factor | Detail |
|--------|--------|
| **Cost** | OSS editor: free. Tina Cloud (managed auth + content API + media): free for 2 editors — no card required for the free tier. Exceeding 2 editors = $29/mo. |
| **Card required?** | No (2-editor free tier). |
| **Auth model** | Tina Cloud manages GitHub OAuth — no separate OAuth proxy needed. This is simpler than Decap's manual proxy setup. |
| **Free tier limits** | Tina Cloud free: 2 editors, unlimited content edits, repo-based storage. GitHub Actions builds: same 2,000 min/mo free. |
| **At the ceiling?** | 2 editors is fine for a solo portfolio. Risk: Tina Cloud is a vendor — if they change pricing or shut down, the CMS breaks. |
| **Media storage** | Tina Cloud + repo, or Cloudinary integration. |
| **Complexity** | Medium. TypeScript schema defines collections. Visual editing for MDX. More opinionated than Decap. |
| **GitHub Pages** | Stays as-is. Rebuild via GitHub Actions. |
| **Blog migration** | Compatible with existing `.md` files; requires schema definition matching frontmatter. |
| **Verdict vs Decap** | Simpler auth setup (no OAuth proxy). Better visual editor. But vendor dependency on Tina Cloud. For a zero-dependency posture, Decap wins. |

**Option A verdict:** **Best fit for zero-cost + GitHub Pages.** Rebuild latency (~60s) is acceptable for a personal portfolio publishing ≤10 posts/month. Decap CMS + Cloudinary is the recommended zero-cost architecture. TinaCMS is an acceptable alternative if Kuldeep prefers the visual editor over zero vendor dependency.

**Hard limit:** Not suitable for real-time content (content goes live after rebuild). Admin writes to GitHub — requires internet + OAuth. Not a concern for a solo developer.

## 2. Option B — External DB + Storage (Dynamic Fetching, GitHub Pages Stays)

**How it works:** Content and media stored in an external managed DB/storage service. Frontend fetches content at runtime via authenticated/public APIs. Admin panel does authenticated writes. GitHub Pages still hosts the SPA.

### B1 — Supabase (PostgreSQL + Storage + Auth)

| Factor | Detail |
|--------|--------|
| **Cost** | Free tier: 500 MB DB, 1 GB file storage, 5 GB egress, 50k MAU auth. |
| **Card required?** | No for free tier. |
| **Free tier ceiling** | 500 MB DB / 1 GB file storage. Sufficient for a text-heavy blog (thousands of posts), but media must be kept off Supabase Storage (use Cloudinary instead). |
| **At the ceiling?** | 500 MB fills up with ~500k words of blog text + metadata. Very unlikely for a personal portfolio. |
| **Auth model** | Supabase Auth (email/password or magic link). RLS protects write paths. |
| **Media storage** | 1 GB free Supabase Storage — use only for thumbnails; offload images to Cloudinary. |
| **Complexity** | Medium-high. Requires: RLS policies, Supabase JS client, env secrets, admin auth flow in panel. |
| **GitHub Pages** | Stays. SPA fetches from Supabase at runtime. No rebuild needed for new posts. |
| **Blog migration** | Existing `.md` files imported to DB as rows (one-time script ~30 lines). |
| **⚠️ CRITICAL RISK** | **Project pauses after 7 days inactivity.** If no visitor hits the DB for 7 days, Supabase pauses it. Site shows empty content until manually unpaused in the dashboard. A personal portfolio that goes unvisited over a weekend is exactly the scenario that triggers this. **NOT RECOMMENDED on free tier.** Pro = $25/mo — fails zero-budget constraint. |

### B2 — Firebase (Firestore + Storage + Auth)

| Factor | Detail |
|--------|--------|
| **Cost** | Spark plan (free): 1 GB Firestore storage, 5 GB Firebase Storage, 50k auth MAU, 10 GB/mo transfer. |
| **Card required?** | No for Spark. **Warning:** upgrading to Blaze (pay-as-you-go for overages) requires a card — but the Spark plan itself does NOT. Do NOT upgrade unless you hit limits. |
| **Free tier ceiling** | 1 GB Firestore (text-only blog = vast headroom), 5 GB Firebase Storage (media), 10 GB transfer/mo. For a personal portfolio: Firestore ceiling unlikely to be hit; 10 GB transfer could be hit if the site gets burst traffic. |
| **At the ceiling?** | Firestore reads: 50k/day free — fine for a portfolio. Storage 5 GB = ~2,500 compressed blog images. Transfer 10 GB/mo = the real ceiling if video is served. **Mitigation: offload video to YouTube embed; serve images via Cloudinary CDN instead of Firebase Storage bandwidth.** |
| **No project pausing** | Unlike Supabase — Firebase Spark does NOT pause. Portfolio stays live indefinitely. |
| **Auth model** | Firebase Auth (email/password or Google). Firestore security rules protect write paths. |
| **Media storage** | Firebase Storage (5 GB). Use for thumbnails/small images. Offload large media to Cloudinary. |
| **Complexity** | Medium-high. Firestore is NoSQL (document model). Security rules are verbose but straightforward for a single-admin write path. |
| **GitHub Pages** | Stays. SPA fetches Firestore at runtime. No rebuild for new posts. |
| **Blog migration** | `.md` files imported to Firestore as documents (body + frontmatter fields). One-time script. |
| **Vendor lock-in** | High. Firebase SDKs are Google-proprietary. Migrating away is painful. |
| **Verdict** | Best managed DB option under zero-budget constraint (no pausing, no card required, generous free limits). Recommended only if Kuldeep wants instant-live publish WITHOUT migrating hosting. Vendor lock-in is the tradeoff. |

### B3 — PocketBase (Self-Hosted)

| Factor | Detail |
|--------|--------|
| **Cost** | PocketBase software: free (MIT). **BUT: requires an always-on server.** A VPS costs ~$5–6/mo (Hetzner CX22, DigitalOcean). **NOT free unless Kuldeep already owns/leases a server.** |
| **Card required?** | Yes — VPS billing. |
| **⚠️ FAILS ZERO-BUDGET CONSTRAINT** | Unless Kuldeep already runs a VPS for another purpose, this is not a free option. **Excluded.** |
| **Render free tier for PocketBase?** | Render free web services spin down after 15 min idle AND have ephemeral disk — SQLite data is **lost on spin-down**. Not usable for PocketBase. |
| **Verdict** | Excluded under zero-budget constraint unless Kuldeep has an existing always-on server. |

**Option B verdict (zero-budget):**  
- **Supabase: excluded** — 7-day inactivity pause kills it.  
- **PocketBase: excluded** — needs paid VPS.  
- **Firebase Spark: viable** — no pausing, no card, 5 GB Storage + 10 GB transfer. Best managed DB option under zero-budget IF Kuldeep wants instant-live publish without changing hosting. High Google vendor lock-in.

**Tradeoff:** All Option B approaches require: (1) managing API keys/secrets, (2) CORS configuration, (3) admin auth flow in the frontend panel, (4) one-time markdown migration. Content is no longer version-controlled in git.

## 3. Option C — Move Hosting (Enables Backend Capability)

**How it works:** Migrate from GitHub Pages to a platform with serverless/edge function support. This unlocks a write API at the same domain — admin panel POSTs to `/api/posts`, the function validates auth and writes to DB.

### C1 — Cloudflare Pages + D1 + R2 — **ZERO COST, BEST LONG-TERM**

| Factor | Detail |
|--------|--------|
| **Cost** | $0. All components are on Cloudflare's free tier indefinitely. |
| **Card required?** | No. Cloudflare free tier never requires a card. |
| **Free tier limits** | Unlimited bandwidth; 500 builds/mo (GitHub Actions trigger); D1: 5 GB SQLite + 5M row reads/day + 100k writes/day; R2: 10 GB storage + 10M Class-B read ops/mo + 1M Class-A write ops/mo + **0 egress fees**; Workers: 100k requests/day. |
| **At the ceiling?** | D1 5M row reads/day and R2 10 GB are enormous for a personal portfolio. The 500 builds/mo limit is the only real ceiling — ~16 blog posts/day if each triggers a build. Not a concern for infrequent publishing. |
| **Auth model** | Cloudflare Pages Function validates admin JWT. Auth identity: use **Clerk free tier** (10k MAU, no card) or a hardcoded API key in a secret (simplest for a single admin). |
| **Media storage** | R2 (10 GB free, zero egress fees). Best CDN delivery of any option. Images served via `r2.dev` public bucket URL. |
| **Complexity** | Medium. Vite SPA deploys identically to GitHub Pages — only the deploy target changes (`wrangler pages deploy` instead of `gh-pages`). Workers Functions directory handles the admin write API. D1 is SQLite-compatible. |
| **GitHub Pages** | **Replaced** by Cloudflare Pages — same workflow (push → build → deploy), adds edge functions. |
| **Blog migration** | Existing `.md` posts seeded to D1 via one migration script. Or keep `import.meta.glob` for existing posts + D1 for new ones (hybrid approach, lower risk). |
| **Rebuild needed?** | No — content served dynamically from D1. Admin writes are instant-live. |
| **Verdict** | Most generous free tier of any option. D1 + R2 + Workers is more capable than Firebase Spark at $0. No vendor lock-in (Cloudflare is infrastructure-level, not SDK-level). Best long-term architecture for this site. |

### C2 — Vercel + KV + Blob

| Factor | Detail |
|--------|--------|
| **Cost** | Free hobby: serverless functions, 100 GB bandwidth/mo, KV (100k reads/day), Blob (5 GB). |
| **Auth model** | Same pattern — API routes handle write path. |
| **Media storage** | Vercel Blob (5 GB). |
| **Complexity** | Similar to Cloudflare Pages. Vite SPA deploys without config changes. |
| **Verdict** | Good option but slightly less generous free tier than Cloudflare (5 GB Blob vs 10 GB R2; egress fees apply). Cloudflare preferred for zero-egress cost. |

**Option C verdict:** Cloudflare Pages + D1 + R2 is the strongest long-term foundation. The migration from GitHub Pages is low-risk — Vite builds identically; the only change is the deploy target and adding a Pages Functions directory for the admin write API.

## 5. Recommendation (Zero-Budget)

Three viable zero-cost paths exist. Ranked:

### 🥇 Best Zero-Cost Architecture: Cloudflare Pages + D1 + R2 (Option C1)

**$0 forever. No card. No inactivity pausing. No egress fees.**

- D1 (SQLite, 5 GB free) maps directly to blog posts + case studies as rows
- R2 (10 GB, zero egress) is the best free media CDN available anywhere
- Vite SPA deploys identically — only the deploy target changes (`wrangler pages deploy` instead of `gh-pages`)
- Admin write path: one Cloudflare Pages Function validates an API key and writes to D1
- Existing `.md` blog posts seeded via a one-time migration script; role theme inheritance fix ships in the same PR
- Recommended **if Kuldeep is willing to move from GitHub Pages to Cloudflare Pages** (same experience for visitors, different deploy mechanism)

### 🥈 Best "Stay on GitHub Pages" Path: Decap CMS + Cloudinary (Option A1)

**$0 forever. No card. Zero hosting change.**

- Decap CMS writes `.md` files to the repo via GitHub API → GitHub Actions rebuilds → Pages deploys
- Cloudinary handles media (10 GB storage + 20 GB CDN free, no card)
- OAuth proxy on Render free tier handles the GitHub OAuth flow (spins up on demand)
- Existing `.md` blog posts: zero migration (natively compatible)
- **60-second rebuild delay** between "Save" and "Live" — acceptable for ≤10 posts/month
- Recommended if Kuldeep wants to stay on GitHub Pages and is OK with rebuild latency

### 🥉 GitHub Pages + Firebase Spark (Option B2)

**$0. No card required (Spark plan). No pausing. Instant-live.**

- More complex than Option A (RLS/security rules, Firebase SDK dependency)
- High Google vendor lock-in
- Viable if instant-live publish is required but Cloudflare Pages migration is off the table
- Not recommended as primary — Cloudflare Pages is a cleaner architecture with better free limits

**Do NOT use:**
- Supabase free tier — inactivity pausing
- PocketBase — needs a paid VPS

## 8. Non-DB Item: Role Theme on Detail Pages

**Not DB-dependent.** The fix is a single change in the app-level layout:

- `useRole()` in `App.tsx` or a global `<Layout>` component sets CSS custom properties on `<html>` via the `?role=` param.
- If `BlogDetailPage` and `ProjectDetailPage` are rendered inside that layout, they inherit the theme automatically.
- If they bypass the layout, add `useRole()` at the top of those pages.
- The `?role=` param must be preserved on navigation to detail pages — check that `<Link>` components include the param.

**Estimated effort:** 1–4 hours. Can ship independently of everything else.

## 9. Relation to PRD-V2.1 (JSON Import)

## 10. Decisions Required from Kuldeep

All options are $0. The choices narrow to:

1. **Hosting:** Stay on GitHub Pages (Option A — Decap CMS, 60s rebuild delay, zero migration) OR migrate to Cloudflare Pages (Option C — D1+R2, instant publish, same zero cost, small migration effort)?
   - This is the most consequential decision. Everything else follows from it.

2. **Rebuild acceptable?** If staying on GitHub Pages: is a ~60 second delay from "Save" to "Live" OK for blog/case study publishing? If yes → Decap CMS. If no → Cloudflare Pages or Firebase Spark.

3. **Google vendor lock-in acceptable?** If staying on GitHub Pages AND rebuild latency is not OK → Firebase Spark is the only zero-cost instant-live option. But all content + auth becomes Google-dependent.

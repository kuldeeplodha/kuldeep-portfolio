## 1. Option A — Git-Based CMS (Stay on GitHub Pages)

**How it works:** A CMS (Decap CMS or TinaCMS) authenticates to GitHub via OAuth, writes Markdown/JSON files directly to the repo, and triggers a GitHub Actions rebuild. Content lives in git; GitHub Pages serves the output.

### A1 — Decap CMS (formerly Netlify CMS)

| Factor | Detail |
|--------|--------|
| **Cost** | Free (MIT open source). Auth proxy needed if not on Netlify — use the community `netlify-cms-oauth-provider` or Decap's own proxy on a free Render/Railway hobby dyno. |
| **Auth model** | GitHub OAuth. A tiny OAuth proxy (Node.js, ~50 lines) accepts the callback and forwards the token to the browser. One free Render/Railway instance suffices. |
| **Media storage** | Git repo (images as files — works for a portfolio, ~100 images max before repo bloats). Optional: Cloudinary integration (25 credits/mo free ≈ 10 GB + 20 GB CDN bandwidth). |
| **Complexity** | Low-medium. Config YAML defines content collections. No schema code. |
| **GitHub Pages** | Stays as-is. Rebuild via GitHub Actions on push. |
| **Blog migration** | Existing `src/content/blog/*.md` files are natively compatible — zero migration work. |
| **Case studies** | Define a new collection pointing at `src/content/case-studies/*.md`. |
| **Rebuild time** | ~30–90 seconds (GitHub Actions). Not instant; suits infrequent publishing. |
| **Maturity** | ~18k GitHub stars, production since 2016 (as Netlify CMS). Editor UI is form-based, not visual. Development pace post-rebrand is slower. |

### A2 — TinaCMS

| Factor | Detail |
|--------|--------|
| **Cost** | Free (OSS editor). Tina Cloud (managed auth + GraphQL API + media) free for 2 editors, then $29/mo. Self-hosted option possible but complex. |
| **Auth model** | Tina Cloud manages GitHub OAuth + content API. Self-hosted uses a custom backend. |
| **Media storage** | Tina Cloud manages media in repo or Cloudinary. |
| **Complexity** | Medium. TypeScript schema defines collections. Visual editing for MDX components. More opinionated than Decap. |
| **GitHub Pages** | Stays as-is. Rebuild via GitHub Actions. |
| **Blog migration** | Compatible with existing `.md` files; may require schema definition to match frontmatter. |
| **Verdict vs Decap** | Better visual editor; higher vendor dependency risk. For a solo developer with infrequent publishing, Decap's zero-vendor approach is safer. |

**Option A verdict:** Best fit for "stay on GitHub Pages + zero hosting cost." Rebuild latency (~60s) is acceptable for a personal portfolio that publishes a few posts per month. Decap CMS recommended over TinaCMS due to zero vendor lock-in.

**Tradeoff:** Not suitable for real-time content (content goes live after rebuild). Admin writes to GitHub — requires internet + OAuth.

## 2. Option B — External DB + Storage (Dynamic Fetching, GitHub Pages Stays)

**How it works:** Content and media stored in an external managed DB/storage service. Frontend fetches content at runtime via authenticated/public APIs. Admin panel does authenticated writes. GitHub Pages still hosts the SPA.

### B1 — Supabase (PostgreSQL + Storage + Auth)

| Factor | Detail |
|--------|--------|
| **Cost** | Free tier: 500 MB DB, 1 GB file storage, 5 GB egress, 50k MAU auth. **Critical limit: project pauses after 7 days inactivity.** Pro = $25/mo. |
| **Auth model** | Supabase Auth (email/password or magic link). Row-Level Security (RLS) protects write paths. |
| **Media storage** | Supabase Storage (1 GB free). Suitable for a small blog/portfolio. |
| **Complexity** | Medium-high. Requires: RLS policies, Supabase client in frontend, env secrets for anon key, admin auth flow. |
| **GitHub Pages** | Stays. SPA fetches from Supabase at runtime. No rebuild needed for new posts. |
| **Blog migration** | Existing `.md` files must be imported to DB as rows (one-time script). |
| **Risk** | **7-day inactivity pause is a production-blocker for a portfolio.** A portfolio may go days without reads. Supabase will pause the project; the site shows empty content until manually unpaused. **Not recommended for GitHub Pages + free tier.** Pro tier removes this but costs $25/mo. |

### B2 — Firebase (Firestore + Storage + Auth)

| Factor | Detail |
|--------|--------|
| **Cost** | Spark (free): 1 GB Firestore storage, 5 GB Firebase Storage, 50k auth MAU, 10 GB/mo transfer. No project pausing. Blaze (pay-as-you-go) activates for overages. |
| **Auth model** | Firebase Auth (email/password, Google). Firestore security rules protect writes. |
| **Media storage** | Firebase Storage (5 GB free). |
| **Complexity** | Medium-high. Firestore NoSQL requires document modeling. Security rules non-trivial for a write-protected admin path. |
| **GitHub Pages** | Stays. Runtime fetching. |
| **Blog migration** | Existing `.md` files imported to Firestore (markdown body + frontmatter fields as doc). |
| **Vendor lock-in** | High. Firebase SDKs are Google-proprietary. |
| **Verdict** | More generous free tier than Supabase (no pausing). But high vendor lock-in + Firestore NoSQL adds complexity for a simple blog/case-study use case. |

### B3 — PocketBase (Self-Hosted, Single Binary)

| Factor | Detail |
|--------|--------|
| **Cost** | Free OSS (MIT). Needs a VPS: ~$5–6/mo (Hetzner CX22, DigitalOcean Droplet). |
| **Auth model** | PocketBase built-in: email/password + OAuth2. Admin dashboard at `/admin`. |
| **Media storage** | Built-in file storage (local disk on VPS). No CDN by default — add Cloudflare proxy ($0). |
| **Complexity** | Medium. Go binary + SQLite. Admin collections UI is intuitive. No managed vendor. |
| **GitHub Pages** | Stays. SPA fetches PocketBase REST API at runtime. |
| **Blog migration** | Existing `.md` files imported via PocketBase API or admin UI. |
| **Verdict** | Best self-hosted option. Full control. Cost = VPS only. Reasonable for someone comfortable with server management, but adds operational overhead for a personal portfolio. |

**Option B verdict:** Firebase best managed option in this group (no pausing, generous free tier). PocketBase best if Kuldeep is comfortable self-hosting. Supabase free tier is unsuitable due to inactivity pausing.

**Tradeoff:** All Option B approaches require: (1) managing API keys/secrets, (2) CORS configuration, (3) admin auth flow in the frontend panel, (4) one-time markdown migration. Content is no longer version-controlled in git.

## 3. Option C — Move Hosting (Enables Backend Capability)

**How it works:** Migrate from GitHub Pages to a platform with serverless/edge function support. This unlocks a write API at the same domain — admin panel POSTs to `/api/posts`, the function validates auth and writes to DB.

### C1 — Cloudflare Pages + D1 + R2

| Factor | Detail |
|--------|--------|
| **Cost** | Free tier: unlimited bandwidth, 100k Worker requests/day, **D1: 5 GB SQLite + 5M row reads/day**, **R2: 10 GB storage + 0 egress fees**. Never expires. Commercial use allowed. |
| **Auth model** | Cloudflare Pages Functions handle admin write path with JWT validation. Supabase Auth or Clerk ($0 free tier) for identity. |
| **Media storage** | R2 (10 GB free, zero egress). Best CDN delivery. |
| **Complexity** | Medium. Vite SPA deploys identically to GitHub Pages. Workers/Functions wrap the DB. D1 is SQLite-compatible. Migration minimal. |
| **GitHub Pages** | Replaced by Cloudflare Pages — same workflow (push → build → deploy), but with edge functions. |
| **Blog migration** | Existing `.md` content imported to D1 once. Or keep build-time bundling for existing posts + DB for new ones. |
| **Rebuild needed?** | No — content served dynamically from D1. Admin writes are instant-live. |
| **Verdict** | **Best long-term architecture.** Most generous free tier of any option. D1 = production-grade SQLite at the edge. R2 = zero-egress media CDN. Workers = serverless admin API. Zero monthly cost for a personal portfolio with low traffic. |

### C2 — Vercel + KV + Blob

| Factor | Detail |
|--------|--------|
| **Cost** | Free hobby: serverless functions, 100 GB bandwidth/mo, KV (100k reads/day), Blob (5 GB). |
| **Auth model** | Same pattern — API routes handle write path. |
| **Media storage** | Vercel Blob (5 GB). |
| **Complexity** | Similar to Cloudflare Pages. Vite SPA deploys without config changes. |
| **Verdict** | Good option but slightly less generous free tier than Cloudflare (5 GB Blob vs 10 GB R2; egress fees apply). Cloudflare preferred for zero-egress cost. |

**Option C verdict:** Cloudflare Pages + D1 + R2 is the strongest long-term foundation. The migration from GitHub Pages is low-risk — Vite builds identically; the only change is the deploy target and adding a Pages Functions directory for the admin write API.

## 5. Recommendation

**For V2.2: Use Cloudflare Pages + D1 + R2 (Option C1)**

**Rationale:**
- Free tier is the most generous ($0 forever, no inactivity pausing, zero egress)
- D1 (SQLite) maps cleanly to the existing content model — blog posts and case studies are rows, not collections of Firestore documents
- R2 removes CDN egress cost entirely for media
- Admin write path: a single Cloudflare Pages Function validates the admin JWT and writes to D1 — same pattern as the existing admin panel, just with persistence
- Vite SPA builds identically; deploy command changes from `gh-pages` to `wrangler pages deploy` (or CI action)
- Existing markdown blog posts can be seeded into D1 in one script, then new posts authored via the admin panel
- Role theme inheritance on detail pages (below) is independent and can ship on either platform

**If Kuldeep wants to stay on GitHub Pages strictly:** Use Option A (Decap CMS). Zero cost, zero hosting change, existing markdown compatible. Accept 60-second rebuild delay per publish. Add Cloudinary for media ($0 free tier). This is the lowest-risk minimum-change path.

**Do not use:** Supabase free tier (inactivity pausing kills it for a portfolio).

## 6. Phased Implementation Plan (Cloudflare Pages path)

| Phase | Work | Outcome |
|-------|------|---------|
| **P0 — Migrate hosting** | Move deploy target from GitHub Pages to Cloudflare Pages. Same Vite build; swap `gh-pages` publish action for Cloudflare Pages action. | Site live on `kuldeeplodha.pages.dev` (or custom domain). Same SPA. Zero regression. |
| **P1 — DB schema** | Create D1 database. Define tables: `blog_posts` (id, slug, title, excerpt, date, tags, roles, body, media_url), `case_studies` (id, slug, title, summary, domain, tech, problem, architecture, outcome, media_url). | Schema in place. Admin can be wired to it. |
| **P2 — Admin write API** | Add `functions/api/posts.ts` (Cloudflare Pages Function) with admin JWT validation. POST = create/update post. DELETE = remove. | Admin panel can create/edit/delete without rebuild. |
| **P3 — Media upload** | Add R2 bucket. Admin panel MediaFields component uploads via a presigned R2 API endpoint. Return `r2.dev` URL stored in post row. | Images/video stored in R2, referenced by URL. |
| **P4 — Admin panel UI** | Add Blog + Case Studies tabs to AdminPage. Form fields matching `BlogMetadata` + case study shape. Preview rendered markdown. | Kuldeep authors in-panel, saves to D1 instantly. |
| **P5 — Archive pages** | Add `/blog` list (latest N + paginated), `/case-studies` list, `/blog/:slug`, `/case-studies/:slug` routes. Homepage shows latest 3 of each. | Full read path live. |

## 8. Non-DB Item: Role Theme on Detail Pages

**Not DB-dependent.** The fix is a single change in the app-level layout:

- `useRole()` in `App.tsx` or a global `<Layout>` component sets CSS custom properties on `<html>` via the `?role=` param.
- If `BlogDetailPage` and `ProjectDetailPage` are rendered inside that layout, they inherit the theme automatically.
- If they bypass the layout, add `useRole()` at the top of those pages.
- The `?role=` param must be preserved on navigation to detail pages — check that `<Link>` components include the param.

**Estimated effort:** 1–4 hours. Can ship independently of everything else.

|---|---|---|

## Core Insight: Split Public Reads from Admin Writes

The single most important architectural decision is **where cold starts land**:

- **Public reads (blog list, blog post, case studies):** Must be fast for visitors. Serve as **static JSON files** generated at build time and hosted on CDN (GitHub Pages or Cloudflare Pages). Zero cold start. Zero DB hit per visitor.
- **Admin writes (create/edit post, upload media):** Only Kuldeep uses these. A 30–60s cold start on first admin login is acceptable.

This split makes the "fast public reads" requirement achievable on any free tier — even one that sleeps.

## 1. FastAPI Hosting Options (Free, No Card)

| Platform | Cold start | Card? | Always-on? | Free limits | Verdict |
|---|---|---|---|---|---|
| **Vercel Python** | 300–800ms | No | Scale-to-zero | 10s exec timeout; 100 GB bandwidth/mo | ✅ Best |
| **Render free** | 30–60s (up to 2-3min) | No | ❌ Sleeps 15min | 750 compute-hrs/mo | ⚠️ Admin-only use OK |
| **Fly.io** | Fast | **Yes** | Configurable | — | ❌ Excluded (card) |
| **HuggingFace Spaces** | Sleeps | No | ❌ Free CPU tier removed 2025 | — | ❌ Excluded |
| **PythonAnywhere** | Sleeps | No | ❌ Free web apps sleep | 1 web app | ❌ Excluded |

### Vercel Python Serverless — Recommended

FastAPI deployed as a Vercel serverless function (via `api/index.py` + `vercel.json`). Cold start 300–800ms after inactivity — well below Render's 30–60s. Scale-to-zero means no persistent compute cost. **10-second execution timeout on free tier** is the key limit: admin write operations (insert post to DB, return 200) complete well within it. Media upload goes directly to Cloudinary (client → Cloudinary API), so FastAPI never handles binary payloads — no timeout risk.

No card required. Deploy via GitHub integration.

**At the ceiling:** 100 GB bandwidth/mo and 6,000 serverless function invocations/day. For a personal portfolio admin panel with ~10 publishes/month, this ceiling is unreachable.

### Render Free — Acceptable Fallback

Simpler deployment (Docker or Python buildpack, no `vercel.json` boilerplate). But 30–60s cold start makes it unsuitable for public-facing API calls. Acceptable ONLY if all public reads are served statically (which is the recommended pattern anyway). Admin cold start of 30–60s on first daily login is tolerable.

## 2. Database (Free, No Card, No Hard Pausing)

| DB | Card? | Storage | Suspend behavior | FastAPI integration | Verdict |
|---|---|---|---|---|---|
| **Neon (Postgres)** | No | 512 MB | Suspends at 5min idle; resumes in ~1.8s | SQLAlchemy + asyncpg | ✅ Best |
| **Turso (libSQL/SQLite)** | No | 5 GB | No suspend | libsql-client or HTTP API | ✅ Good alt |
| **Supabase free** | No | 500 MB DB | **Hard pause 7 days** | — | ❌ Excluded |

### Neon — Recommended

Serverless Postgres. No credit card. 512 MB storage (thousands of blog posts — never a concern). Auto-suspends after 5 min idle; resumes in ~1.8s median. Since public reads are static (no DB hit), the only Neon calls are admin writes — cold resume of 1.8s on admin save is invisible. Standard Postgres = SQLAlchemy + asyncpg + Alembic migrations, all first-class FastAPI patterns.

**At the ceiling:** 512 MB fills only with millions of text rows. 100 compute-hours/mo free — admin writes of ~1s each means ~360,000 writes before hitting limit. Not a concern.

### Turso — Acceptable Alternative

5 GB free, 500M row reads/mo, no card, no suspend ever. libSQL is SQLite-compatible. HTTP API works from Vercel serverless without native binaries. Simpler than Postgres but less familiar tooling in Python (no SQLAlchemy native driver yet; use HTTP client or `libsql-client`). Choose Turso if Kuldeep prefers zero-suspend guarantees or SQLite simplicity.

## 4. Media — Cloudinary (Confirmed No Card)

Cloudinary free tier: **10 GB storage + 20 GB CDN bandwidth + 25 credits/mo**. No credit card required. No project pausing. Commercial use allowed.

**Upload pattern (keeps API secret safe):**
1. Admin panel requests a signed upload URL from FastAPI (`GET /api/media/sign`)
2. FastAPI signs the request using Cloudinary API secret (stored in Vercel env var, never exposed to browser)
3. Browser uploads directly to Cloudinary with the signed URL — FastAPI never handles the binary payload
4. Cloudinary returns the public URL; admin panel stores it in the post record

This pattern avoids Vercel's 4.5 MB request body limit and keeps the API secret server-side only.

## 5. Admin Auth (No External Service)

Single admin (Kuldeep only) → simplest viable approach: **hardcoded API key in a Vercel environment variable**.

```python
# FastAPI dependency
from fastapi import Header, HTTPException
import os

ADMIN_KEY = os.environ["ADMIN_API_KEY"]  # Set in Vercel dashboard

async def require_admin(x_admin_key: str = Header(...)):
    if x_admin_key != ADMIN_KEY:
        raise HTTPException(status_code=401)
```

Admin panel sends `X-Admin-Key: <secret>` header on all write requests. The key never appears in client-side code (stored in browser only during the session, or in a local `.env` the human never commits). No JWT library, no OAuth flow, no external service.

For stronger security later: swap to a short-lived JWT signed by a secret — still no external service, just `python-jose` (~50 lines).

```
                  No card · 10 GB storage · 20 GB CDN · signed upload via FastAPI

ADMIN AUTH        Env-var API key in Vercel (single admin)
```

**Total monthly cost: $0. No credit card on any component.**

## 7. Cold-Start Mitigation for Public Reads

Public readers never hit FastAPI or Neon. The pattern:

1. **On each admin publish:** FastAPI writes post to Neon, then triggers a GitHub Actions workflow (via `workflow_dispatch` API call) that regenerates static JSON files and redeploys to GitHub Pages.
2. **Public SPA fetches static JSON** from GitHub Pages CDN — sub-100ms, globally cached, zero cold start.
3. **Admin panel fetches live from FastAPI** — 300–800ms cold start acceptable.

This is the same pattern that makes Decap CMS (from v2.2-cms-db-research.md) work, but with a FastAPI admin API instead of a Git-based CMS.

## 9. Decisions Required from Kuldeep

1. **FastAPI host:** Vercel (300–800ms cold start, simpler) OR Render (30–60s cold start, simpler deployment but slower admin UX)?
   - Recommendation: Vercel.

2. **DB:** Neon Postgres (standard SQL, SQLAlchemy) OR Turso libSQL (5 GB, never suspends, lighter but less Python tooling)?
   - Recommendation: Neon. Turso if zero-suspend guarantee matters more than tooling familiarity.

3. **Publish flow:** On admin save, trigger a GitHub Actions rebuild (blog list updates in ~60s after publish) OR accept that visitors see old static list until next manual redeploy?
   - Recommendation: Auto-trigger rebuild. Adds ~60s delay but keeps public reads fully static.
